# 云同步与备份协议（iCloud / OneDrive）

本文描述「书影记录」当前版本的数据库快照备份与多设备同步协议，对应实现：
`app/cloud_sync.py`、`app/ui/data_page.py`、`app/ui/main_window.py`；
安装界面打包部分另见 `packaging/build_macos.sh`，不属于本协议。

## 1. 设计目标与边界

| 项 | 说明 |
|---|---|
| 同步载体 | 一个**完整的 SQLite 数据库快照文件**，不是按条目的增量同步 |
| 云端目录 | 普通文件夹（iCloud 云盘 / OneDrive / Dropbox / 自定义），不依赖任何云 SDK，不在应用内登录 |
| 冲突策略 | 整库「云端最新覆盖」或「保持本地」，**不做字段级合并** |
| 不参与同步 | 登录 Cookie、书库路径、同步目录、自动开关、同步模式、主题外观、头像路径等本机设置；封面图片（`cache/covers`）等设备级缓存、报告产物 |

> 使用中的数据库不会直接放进同步目录，避免多设备并发写、iCloud 异步上传、占位文件导致数据库损坏。

## 2. 同步目录与文件结构

同步根目录按优先级自动探测（也可手动指定，或用环境变量 `SHUYINGJILU_SYNC_DIR` 覆盖）：

1. macOS `~/Library/Mobile Documents/com~apple~CloudDocs`（iCloud 云盘）
2. Windows `%USERPROFILE%\iCloudDrive` / `iCloud Drive`（iCloud for Windows）
3. `OneDrive` / `OneDriveConsumer` 环境变量及家目录下的 `OneDrive`、`Dropbox`

应用在根目录下创建子目录 `书影记录/`；若用户选定的目录本身就叫 `书影记录`
（或通过 `SHUYINGJILU_SYNC_DIR` 直接指向它），则直接在其中读写，与 iOS 端规则一致。结构如下：

```
<同步根目录>/书影记录/
├── douban_trace_20261119_110227_c3d4_auto.db      # 快照（完整 SQLite 库）
├── douban_trace_20261119_081027_ece5_auto.db
├── douban_trace_20261118_091027_ece5_manual.db
├── ...（每台设备：自动 3 份 + 手动 2 份）
├── latest.json                                     # 最近一次快照的清单
└── devices.json                                    # 设备标记到可读名称的映射（仅展示）
```

## 3. 快照命名规则

```
douban_trace_<YYYYmmdd_HHMMSS>_<设备标记>_<auto|manual>[_序号].db
```

| 字段 | 说明 |
|---|---|
| `YYYYmmdd_HHMMSS` | 生成本地时间（文件名即展示时间；跨设备时钟不准会影响排序） |
| 设备标记 | `sha1(主机名)[:4]`，4 位十六进制，用于区分设备与按设备保留 |
| `auto` / `manual` | 自动备份 / 手动备份；旧版无标记的文件按 `manual` 处理 |
| `序号` | 同一秒内多次生成时的去重后缀 `_2`、`_3`… |

## 4. 快照生成流程（`create_snapshot`）

1. 计算当前库的**逻辑状态指纹** `state_id`：对全部业务表（不含本机设置）逐行做 SHA-256，取前 16 位。
2. 非强制备份且 `state_id == 上次备份状态`、且清单指向的快照仍存在（本机文件或
   `.<名称>.icloud` 占位都算存在）→ **跳过**（内容没变不重复上传；也不会因为
   最新快照被 iCloud 驱逐，就新建一份把清单指向本机旧数据）。
3. 用 SQLite 在线备份 API（`source.backup(target)`）写出临时文件 `.<名称>.part`，保证一致性。
4. 从快照中删除本机专属设置（`LOCAL_SETTING_KEYS`），避免把本机 Cookie / 路径带到其他设备；
   同时写入快照元数据 `snapshot_marks_version = '1'`，声明这份快照完整维护 `ignored_subjects` / `purged_records`（见 9.2.3）。
   另外把影片时长写入 `movie_meta` 表：优先取本机缓存，缓存没有的从记录简介（如「122分钟」）解析补齐，
   这样换设备恢复后无需再逐条向豆瓣请求。
5. 统计各表行数（`records`、`doulists`、`doulist_items`、`plan_folders`、`plan_items`、`book_words`、`book_meta`、`movie_meta`、`ignored_subjects`、`purged_records`），并额外拆出 `records_movie` / `records_book`。
6. 计算 SHA-256、原子改名落盘，写入 `latest.json`，再执行保留策略。
7. 记录本机簿记：`cloud_sync_last_state`、`cloud_sync_last_time`、`cloud_sync_last_snapshot`。

### 本机专属设置（不进快照，恢复时保留）

`douban_cookie`、`book_library_dir`、`cloud_sync_dir`、`cloud_sync_last_state`、`cloud_sync_last_time`、`cloud_sync_last_snapshot`、`cloud_sync_auto_backup`、`cloud_sync_auto_sync`、`sync_mode`、`theme`、`report_theme`、`display_avatar`

## 5. 清单文件 `latest.json`

记录最近一份快照，用于判断「云端是否有更新」和校验完整性：

```json
{
  "snapshot": "douban_trace_20261119_110227_c3d4_auto.db",
  "created_at": "2026-11-19 11:02:27",
  "created_ts": 1795000000,
  "tag": "c3d4", "platform": "macOS", "arch": "arm64",
  "device": "MacBook-Office",
  "app_version": "0.1.1",
  "sha256": "…",
  "size": 503808,
  "kind": "auto",
  "records_updated": "2026-11-19T11:10:00",
  "counts": {
    "records": 318, "records_movie": 160, "records_book": 158,
    "doulists": 40, "doulist_items": 250,
    "plan_folders": 3, "plan_items": 28,
    "book_words": 63, "book_meta": 159, "movie_meta": 160,
    "ignored_subjects": 2, "purged_records": 5
  }
}
```

## 6. 保留策略

| 维度 | 规则 |
|---|---|
| 分组 | 按（设备标记, 备份类型）分组，**互不干扰** |
| 自动备份（auto） | 每台设备保留最新 **3** 份 |
| 手动备份（manual） | 每台设备保留最新 **2** 份 |
| 排序 | 按「时间戳 + 同秒序号」倒序（与 iOS 一致），超出部分删除 |
| 未下载占位 | iCloud 未落地的 `.xxx.db.icloud` 同样参与计数与清理 |

> `devices.json` 只用于历史快照的设备名展示，不参与快照校验、恢复或保留策略；iOS v1.3+ 也会合并写入。
>
> 多设备共用一个目录时，各设备只清理自己的记录，不会挤掉其他设备的快照。
> 本机恢复前的安全备份另存于 `<数据目录>/backups/`，保留最近 5 份，不上云。

## 7. 校验与恢复（`restore_snapshot`）

### 7.1 校验

1. 快照文件必须存在（若只有 `.name.db.icloud` 占位则提示「尚未下载到本机」）。
2. `PRAGMA integrity_check` 必须为 `ok`。
3. 必须包含 `records`、`settings`、`doulists`、`plan_folders` 四张表，否则判定「不是书影记录数据库快照」。
4. `latest.json` 带 `sha256` 时比对文件哈希，防止同步未完成就恢复。

### 7.2 恢复步骤

1. 保存本机设置：`douban_cookie`、`book_library_dir`、`cloud_sync_dir`、`sync_mode`、`theme`、`report_theme`、`display_avatar`。
2. 把当前库复制到 `<数据目录>/backups/douban_trace_before_restore_<时间>.db`（保留 5 份）。
3. 用快照覆盖本地数据库 → 重新执行建表与迁移（`_init_schema`，会补上旧快照缺的列与 `movie_meta` 表）。
4. 回填本机设置；把数据库里的书籍页数与影片时长同步回本机缓存（`book_meta` → `cache/book_meta.json`，`movie_meta` → `cache/movie_meta.json`）。
5. 应用侧车：写回自定义封面（base64）、记录封面地址（`coverURL`，仅回填空值）、豆列条目展示字段、计划条目展示字段、影片时长（`durationMinutes`）。
6. 用恢复前的本机备份回填快照里为空的 `cover_url` / `cover_path`（iOS 快照这两列为空），路径已失效时再兜底查 `cache/covers/<类型>_<ID>.jpg`；豆列/计划条目缺封面时，从同豆瓣条目的记录里借用（`fill_item_covers_from_records`）。
7. `ignored_subjects` / `purged_records` 按 9.2.3 的规则处理（带标记覆盖，老快照空表保留本机）；恢复后**自动**检查缺失的封面 / 书籍页数 / 影片时长并在后台补全（`BackfillWorker`，右上角显示进度，失败会提示风控，可登录豆瓣后重试）。
8. 删除快照元数据键 `snapshot_marks_version`，再更新簿记：`cloud_sync_last_state / last_time / last_snapshot`。

### 7.3 恢复选择

用户「检查并恢复」时列出目录内全部快照，展示：时间（含相对时间）、类型（自动/手动）、来源设备、
记录数（影视/读书拆分）、豆列/计划/字数规模、最近数据更新时间、文件大小、创建版本、是否为本机上次备份、
校验状态；并给出**与本机当前数据对比**（影视/读书/豆列/计划 的 ± 差值），可任选一份恢复。

## 8. 自动备份

开关：`cloud_sync_auto_backup`（本机设置，默认关）。

| 触发时机 | 行为 |
|---|---|
| 记录/豆列/计划等数据变动 | 30 秒防抖，合并连续改动后生成一份 `auto` 快照 |
| 豆瓣同步成功 | 5 秒后生成 |
| 应用退出 | 关闭前再补一次 |
| 内容未变 | `state_id` 相同且清单有效 → 跳过 |

- 未勾选时不产生任何自动草稿；「立即备份」始终生成 `manual` 快照。
- 手动备份前会把本机缓存中的历史页数迁移进数据库（仅此一处做迁移，避免本地旧数据被自动写库）。

## 9. 自动同步

开关：`cloud_sync_auto_sync`（本机设置，默认关）。触发时机：启动后约 2 秒、以及打开该开关的当下。

判定顺序（全部满足才恢复）：

1. 同步目录存在且 `latest.json` 可读、快照文件已存在；
2. 清单快照名 ≠ 本机 `cloud_sync_last_snapshot`（云端确实有新版本）；
3. 本机 `state_id` 与 `cloud_sync_last_state` 一致（本机无未备份改动），**或**本机库为空（新设备首次使用）。

任一条件不满足 → 跳过，不改动本地数据。

### 数据不一致时的处理（现状）

| 情况 | 处理 |
|---|---|
| 本地干净 + 云端有更新 | 覆盖本地（先备份到 `data/backups/`），提示「已自动同步云端数据」 |
| 本地有未备份改动 | 跳过；待数据变动 30 秒后或退出时自动备份，下次启动再同步 |
| 云端与本机上次备份相同 | 无操作 |
| 新设备空库 | 直接拉取云端最新快照 |
| 快照缺失 / 未下载 / 校验失败 | 跳过，本机保持原样 |

自动备份与自动同步**互不串联**：自动同步不会先触发一次备份，也不做冲突合并；会话运行期间不会自动覆盖本地数据。

## 9.1 与 iOS 端兼容（v1.3）

iOS 端（`BookFilmJournal-iOS`）使用同一套目录、命名、清单与 SQLite schema。桌面端在其基础上做了以下兼容：

| 项目 | 兼容处理 |
|---|---|
| iOS 侧车文件 `<快照>.db.ios.json` | 桌面端会读取其中三部分（见下三行）；侧车不参与 `sha256` / 大小计算；清理旧快照时连同侧车一起删除 |
| 侧车 `records[]` 的 `durationMinutes` / `pages` / `coverURL` / `coverData` | 恢复时写入影片时长缓存与 `cache/covers/`、回填记录/豆列/计划封面路径；`coverURL` 只在记录 `cover_url` 为空时补入，`pages` 只在 `book_meta` 缺页数时补入 —— 这样大部分封面/页数/时长不必再联网补全 |
| 侧车 `doulistItems` | 豆列条目的时长/页数/字数/年份/上映日期/评分/短评/简介/创建时间（桌面数据库没有这些列时靠侧车保留），按 `listKey`（`douban:<ID>` 或 `local:<类型>:<标题>`）匹配 |
| 侧车 `planItems` | iOS 写入计划条目的阅读状态/统计文本/上映日期/备注/来源/来源 ID；桌面端不写这段（数据都在 `plan_items` 列里），恢复时只补空值：`releaseDate`/`note`/`source`/`sourceID` 仅在列为空时填入，`isRead == false` 且状态为 `done` 时改为 `wish`；`statsText` 是展示文本，不写入 `plan_items.note` |
| `settings.ios_explore_sites` | 生成快照时按 iOS 结构写入（`id/name/urlString/searchURLTemplate/kind/isLocal`）；恢复 iOS 快照且没有桌面键时，自动转成探索空间站点 |
| 影片时长 | 桌面端固化在 `movie_meta` 表随快照同步；恢复 iOS 快照时另外读取侧车 `durationMinutes` 补进缓存与 `movie_meta`（不覆盖手动值） |
| 自定义封面 | 生成快照时把豆瓣无法重新获取的封面（`manual_*`、其他条目链接封面）以 base64 写入侧车 `coverData`（单张上限 4 MB），恢复时写回 `cache/covers/` 并更新记录/豆列/计划封面路径；记录卡片右上角显示「同步」标记；豆瓣同步遇到自定义封面时保留本地路径，不会被豆瓣封面顶掉；恢复后还会用恢复前的本机备份回填快照里为空的 `cover_url` / `cover_path`（iOS 快照这两列是空值），本机已下载的封面不会因此丢失 |
| `doulists.douban_id = ios-local-<UUID>` | 桌面端按本地豆列处理；豆列跳转使用 `url` 字段，不受影响 |
| `ignored_subjects` / `purged_records` | iOS ≤ v1.2 快照中为空表；两端都按 `settings.snapshot_marks_version` 区分新旧快照，旧快照两表为空时保留本机标记（详见 9.2.3）；iOS v1.3+ 读写这两张表并写同一个标记 |
| 时间字段格式 | 桌面端写 ISO-8601（带时区，如 `2026-11-25T17:52:00+08:00`），iOS 写 `yyyy-MM-dd HH:mm:ss`（本地时间）；两端解析都兼容这两种格式 |
| `devices.json` | 两端都写入并合并（`设备标记 → 名称/平台/架构/最后出现`），仅用于列表展示，不参与校验、恢复与保留 |
| 未下载占位 `.xxx.db.icloud` | 两端都会把占位列出来并标记「未下载」（不会误判成已备份）；桌面端恢复被拒并提示先下载，生成快照时把占位视为「已备份」，避免用本机旧数据顶掉云端最新 |
| 封面 / 字数缓存 | 封面图片文件与字数缓存本身都不进快照；自定义封面以 base64 存放在侧车，桌面端恢复时会导入；豆瓣封面可在新设备重新补全 |

快照命名排序按「时间戳 + 同一秒序号」，同一秒内不会复用基础名，避免清理后重建导致误删最新快照。

## 9.2 换源忽略与彻底删除墓碑（ignored_subjects / purged_records）

这两张表是「防止豆瓣同步把已经处理掉的条目又加回来」的本地抑制表，**必须随快照同步**，否则换设备后会重新出现重复条目或已删除条目。

### 表结构

```sql
CREATE TABLE ignored_subjects (
    media_type TEXT NOT NULL,          -- movie / book
    subject_id TEXT NOT NULL,          -- 被忽略的豆瓣条目 ID
    created_at TEXT NOT NULL DEFAULT '',
    PRIMARY KEY(media_type, subject_id)
);

CREATE TABLE purged_records (
    media_type TEXT NOT NULL,          -- movie / book
    subject_id TEXT NOT NULL,          -- 豆瓣条目 ID
    status TEXT NOT NULL DEFAULT 'done',  -- done / wish（同一作品可有两种状态）
    title TEXT NOT NULL DEFAULT '',
    purged_at TEXT NOT NULL DEFAULT '',
    PRIMARY KEY(media_type, subject_id, status)
);
```

### 9.2.1 `ignored_subjects`：换源后的旧条目抑制

- **写入**：记录换源（`change_record_source`）到另一个豆瓣条目时，把**旧** `(media_type, subject_id)` 写入；
- **解除**：换回该来源、或手动新增该条目记录时删除对应行（`unignore_subject` / `add_manual_record`）；
- **消费**：豆瓣全量/增量同步（`upsert_records`）与 Excel 导入（`import_records`）遇到命中行直接跳过，避免换源前的旧条目作为新记录再次出现；
- **界面**：应用设置「清空本地配置」会提示并清空该表，清空后旧条目可能重新同步回来。

### 9.2.2 `purged_records`：彻底删除的墓碑

- **写入**：回收站里「彻底删除」时（`hard_delete_record`）写入 `(media_type, subject_id, status, title, purged_at)`；
- **解除**：手动新增同 `(media_type, subject_id, status)` 记录时删除对应墓碑；
- **消费**：豆瓣同步（`upsert_records`）与 Excel 导入（`import_records`）遇到命中行跳过，避免已彻底删除的条目被重新加回；
- **跨设备**：Excel 导出包含「彻底删除」与「换源忽略」两张工作表，导入时回填（`import_purged_records` / `ignore_subject`），用于在设备之间传播删除意图。

### 9.2.3 快照与恢复要求（桌面 / iOS 一致）

1. **备份**：`ignored_subjects`、`purged_records` 的**全部行**写入快照，不因设备不同而清空；
2. **恢复**：整表覆盖本机数据，恢复后立即生效（下一次同步即按新表跳过）；
3. **权威标记**：维护这两张表的客户端在写快照时，必须在 `settings` 写入
   `snapshot_marks_version = '1'`（桌面端每次生成快照都会写）。恢复时快照带该键，
   就按快照整表覆盖——**空表代表用户确实清空了标记**；该键只是快照元数据，
   恢复完成后从本机设置中删除；
4. **旧快照兼容**：没有该键的快照视为「老客户端生成」（iOS ≤ v1.2）。此时若快照
   带 `.db.ios.json` 侧车或 `settings.ios_explore_sites`，且两张表为空，则从恢复前的
   本机备份中把这两张表**保留下来**，避免把用户已清理的条目加回来；
5. **iOS 兼容**：iOS v1.3+ 已写快照导出这两张表、恢复时覆盖、删除/换源时维护，并写入 `snapshot_marks_version = '1'`；iOS 恢复带标记快照时按快照覆盖，旧 iOS 快照仍保守保留本机标记；
6. **恢复后清理**：`snapshot_marks_version` 只是快照元数据，桌面端恢复完成后会从本机 `settings` 删除，避免影响状态指纹与下一次生成的快照；

### 9.2.4 丢失后的影响

| 表丢失 | 现象 |
|---|---|
| `ignored_subjects` | 换源前的旧条目在下次豆瓣同步后重新出现，形成重复记录 |
| `purged_records` | 已彻底删除的条目在下次豆瓣同步或导入旧 Excel 后复活 |

## 10. 跨设备与 iCloud 注意事项

- 设备身份仅由主机名哈希决定，不涉及账号；同一台机器重装系统后主机名不变则标记不变。
- iCloud 未下载的文件以 `.xxx.icloud` 占位出现：列表会标注「尚未下载」，恢复前需等待同步完成。
- 快照时间取自文件名与清单，**时钟偏差**会影响跨设备排序；保留策略按各自设备分组，不受影响。
- 快照本体不含封面图片与登录态（自定义封面在侧车中）：新设备恢复后按提示从豆瓣补全普通封面；书籍页数与影片时长已分别随 `book_meta`、`movie_meta` 表同步，无需重新拉取。
- 应用版本记录在清单中；版本差异较大时界面会提示「可能不完全兼容」，建议两端使用同一版本。

## 12. 已知限制

1. 不做三向合并：两台设备同时改动时，只有「云端最新」或「本地」一方生效，另一方需从 `data/backups/` 找回。
2. 封面文件、字数解析结果等设备级缓存不随快照迁移（豆瓣无法获取的自定义封面通过侧车同步，见 9.1）；换机后普通封面需重新补全。
3. 自动同步只在启动/开启开关时检查一次，运行中不会后台轮询。
4. 没有 `snapshot_marks_version` 的旧快照仍按「侧车 / `ios_explore_sites` + 两表为空 → 保留本机标记」保守处理；升级前的老桌面快照带侧车，在 iOS 上也会被当作老 iOS 快照保留本机标记（不会丢数据，只是覆盖不彻底）。
5. 恢复是整库替换，恢复后需重新打开相关页面（应用会自动刷新）。
